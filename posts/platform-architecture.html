平台架构怎么制定：从平台边界到变体矩阵

2026-11-02 · 9 MIN READ · 电子电气架构 · 平台化

平台到底是什么

平台不是「一套所有车都能用的方案」，而是一组可复用的技术基线，加上一套受控的变体机制。 两个要素缺一不可：只有基线没有变体，做完就是最大公约数；只有变体没有基线，等于每个项目各做各的。

判断一个平台是否成立，只看一件事：新增一个车型时，需要改动的差异点是否被清晰枚举、且数量可控。 如果每次新车型都要「现场再说」，那不是平台，是复用了一次的项目。

制定的五个步骤

  1. 划定平台边界：覆盖哪些车型级别、哪些动力形式、生命周期几年。 边界写不清楚，后面所有决策都会失焦。
  2. 功能清单与分级：把功能拆成「全系必备 / 选装 / 区域特有」三级。 分级决定了哪些进基线、哪些进变体。
  3. 功能分配到节点：谁算、谁显示、谁存储。分配原则见后文，本质是就近、实时、隔离与成本的折中。
  4. 通信骨架：几段 CAN、是否上以太网骨干、网关放在哪、跨段路由规则。 骨架一旦定了，后面所有节点的接口都得服从它。
  5. 变体机制：硬件变体、软件变体、配置字三层，各自负责不同粒度的差异。
顺序不能换：先定变体机制再定通信骨架，会导致每加一个变体就多一段网络； 先定功能分配再定功能清单，会导致功能被节点能力反向裁剪。

变体机制怎么设计

差异分三层管理，越往下改动成本越低、风险越小：

层级承载什么差异改动代价典型手段
硬件变体接口数量、屏幕尺寸、功率等级高不同料号、可选贴装
软件变体功能有无、策略差异、区域法规中编译开关、功能包
配置字参数、阈值、标定、使能位低EOL 写入、诊断写入

设计的核心目标是把差异尽量往下层压：能用一个配置位解决的，绝不新开一个硬件料号； 能用功能包切换的，绝不编译两套软件。

variant_config.h
typedef struct {
    uint8_t  platform;      /* 平台代号，决定基线版本 */
    uint8_t  screen_type;   /* 7" / 10.25" / 12.3" */
    uint8_t  region;        /* 法规区域，影响图标与语言 */
    uint16_t feature_bits;  /* 位域：哪 16 个可选功能被使能 */
    uint32_t checksum;      /* 配置完整性校验 */
} variant_cfg_t;

配置字必须有校验，且损坏时能回落到一个安全的默认配置。 配置字丢失导致功能全开的案例，在量产车上并不罕见。

复用度怎么量化

「我们复用得很好」是没法评审的。至少要有四个可量化指标：

  • 功能复用率：平台功能数 / 车型功能总数
  • 差异点数：每个新车型相对基线的变更条目数，应呈收敛趋势
  • 配置项数量：配置字位宽增长曲线，失控前必须收敛
  • 变体组合数：理论组合数 vs 实际出货组合数，差距越大说明设计冗余越多

其中差异点数最有说服力：第一个车型 200 条、第二个 120 条、第三个 60 条， 这是健康曲线；如果一直在 180 条上下，说明平台没有真正沉淀。

三种典型失败

  1. 最大公约数陷阱：为了兼容所有车型，把功能做到最低配， 结果每个项目上线后都要加回自己的需求，平台变成了负担。
  2. if-else 硬化：差异用代码里的条件分支实现，而不是配置。 车型一多，代码复杂度指数上升，谁也不敢改。
  3. 配置字爆炸：每个新需求都加一个配置位，最终几十个位互相耦合， 没有任何人能说清某个组合是否合法。
解法：配置字要有「合法组合表」，非法组合在 EOL 阶段就被拒绝写入， 而不是等到整车下线后才发现某个功能永远打不开。

平台治理

平台最难的不是设计出来，而是守住它。三条规则比较有效：

  • 准入：新需求进入平台基线前，必须证明「无法用现有变体机制满足」
  • 基线冻结：每个年型一条基线，冻结后只接受缺陷修复，功能变更走下一个基线
  • 反向验证：每季度用最近三个车型的差异点反推平台设计缺陷，形成改进项

平台的价值不在第一年体现，而在第三年——当新车型的开发周期和缺陷率明显低于第一个车型时， 平台才算真的成立。

两层规划：策略与架构书

成熟的电子架构平台，规划通常是两层，而不是一份文档一次写到底：

  1. 架构策略：基于竞品对标与产品属性分析，规划平台级方案——回答「这个平台整体怎么做」，产出平台架构方案、整车功能清单、ECU 清单。
  2. 电子架构书：在策略之上，结合 ECU 清单分析与功能清单分析，论证各域方案的合理性，落到具体车型——回答「这台车怎么做」，明确拓扑、网络与功能分配。

两层的关系是「平台 → 项目」的两次裁剪：策略承担复用与前瞻，架构书承担落地与取舍。跳过策略直接写架构书，每台车都像从零开始；只有策略没有架构书，平台永远落不了地。

判据：如果一个平台的「策略」文档和「架构书」文档内容几乎一样，说明要么策略写成了项目方案，要么架构书在抄策略——两者必有一个失效。
