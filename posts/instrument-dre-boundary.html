组合仪表 DRE 的责任边界

2026-09-12 · 7 MIN READ · 汽车电子 · DRE

DRE 到底负责什么

DRE 是 Design / Development Responsible Engineer，字面是「设计开发责任人」， 实际落到项目里，是这个零部件从承接需求到量产后维护的唯一责任接口。 它不是一个「画图岗」，也不是「催供应商的岗」，而是技术状态的最终背书人。

拆开看是三段责任，缺一段都会在量产后还回来找你：

  • 需求承接：把整车层面的功能描述，翻译成可验证的零部件指标
  • 方案实现：定接口、定边界、定失效策略，并证明它成立
  • 量产维护：版本、变更、问题闭环，保证技术状态始终一致
判断标准：出现任何一个仪表相关的问题，如果没人能立刻说出「谁定义、谁验证、谁批准变更」， 那这个项目的 DRE 责任就是没闭环的。

四个交付节点

  1. 需求冻结：PRD / SRD 完成评审并基线化，此后变更走 ECR
  2. 方案冻结：接口矩阵（IC）、DFMEA、BOM、图纸定版，供应商锁定软硬件版本
  3. 样件验证：DVP&R 全部执行完，问题清单 A 类清零
  4. SOP：量产状态确认、技术文件归档、售后与备件接口交接

节点之间最常见的失控，是「方案冻结了但接口还没对齐」—— 尤其是仪表与网关、车身控制器之间的信号来源，往往在样件阶段才发现两边各接了一路。

交付物清单

交付物回答什么问题失效后果
PRD / SRD要做什么、被谁使用需求漂移，测试无依据
接口矩阵 IC和谁交换什么、周期多久信号缺失/重复，联调返工
DVP&R怎么证明它成立问题逃逸到量产
DFMEA失效模式与探测手段高风险项无预防措施
BOM / 图纸物料与几何状态装了不对的件
ECR / ECO变更是否被批准并落地台架对、实车不对
问题清单每个问题的闭环证据问题反复，责任不清

与 FO / SO 的分工

三个角色经常被混着叫，实际边界可以用一句话切开：

  • FO（Feature Owner）定「做什么、为什么」——用户场景、功能需求、验收标准
  • SO（System Owner）定「怎么连」——系统边界、接口、时序、失效降级
  • DRE定「做出来、验明白、管到底」——实现方案、验证证据、量产技术状态

实践中越界最典型的是：FO 直接给 DRE 一个界面稿，SO 直接给一个信号列表， 然后 DRE 拿着两份互相矛盾的材料开工。正确做法是把冲突显性化—— 由 SO 出接口基线，FO 出功能基线，DRE 只对「基线是否可实现」提异议， 而不是在实现阶段替上游做决策。

五个高危接口

  1. 信号来源不唯一：同一路车速既有网关转发又有硬线，两路超时策略不一致， 表现为「偶发跳变」。
  2. 唤醒源与休眠冲突：仪表被 CAN 唤醒后立即进入显示，但此时整车还没上电， 出现「黑屏闪一下」。
  3. KL15 掉电存储窗口：掉电到 NVM 写完之间只有几十毫秒， 小计里程、用户设置最容易丢。
  4. 背光调光曲线：整车给的占空比与仪表亮度不是线性关系， 夜间最低亮度刺眼、白天又偏暗。
  5. 样件状态与技术状态不一致：台架上是 V2 软件，实车装的是 V1， 问题复现不了，白白排查两周。

收尾清单

  • 接口矩阵的每一行，都能对应到一个 DBC 报文和一个测试用例
  • 每个 A 类问题都有「复现条件 + 根因 + 整改 + 回归」四段证据
  • 供应商交付版本与本方台架版本完全一致，且有版本记录
  • 售后手册里没有出现「以实车为准」这类无法追溯的描述

这四行看起来像流程话，但它们是量产之后你还能睡得着觉的原因。
