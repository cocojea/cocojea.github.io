报警策略与优先级仲裁

2026-10-21 · 8 MIN READ · 汽车电子 · 功能策略

报警不是布尔量

新手最常见的实现是「条件成立 → 点灯」，然后很快遇到三个问题： 条件抖动导致灯闪、多个条件同时成立导致灯打架、故障恢复后灯不灭。 根因是把报警当成了布尔量，而它其实是一个带生命周期和优先级的对象。

alarm_object.c
typedef struct {
    uint16_t id;
    bool     raw;        /* 原始触发条件 */
    bool     active;     /* 去抖后为真 */
    uint8_t  prio;       /* 0 最高 */
    uint8_t  slot;       /* 显示槽位，同槽位互斥 */
    uint8_t  color;      /* 红/黄/绿/蓝 */
    uint8_t  blink;      /* 0 常亮, 1Hz, 2Hz */
    uint16_t t_on;       /* 触发去抖时间 ms */
    uint16_t t_off;      /* 恢复去抖时间 ms */
    bool     inhibited;  /* 被抑制（自检/欠压/更高优先） */
} alarm_t;

slot 是这份结构里最容易被忽略的字段。 没有它，两个报警会同时画在同一个位置，最后渲染成谁也看不懂的叠影。

优先级从哪来

优先级不是拍脑袋排的，通常由三个来源叠加决定：

  1. 法规强制：图形标志、颜色、闪烁频率有明确要求，不可自定义
  2. 安全相关：影响驾驶判断的（制动、转向、电池热失控）必须最高
  3. 用户感知：提示类信息的次序按用户关注度排，而非按 ECU 上报顺序

一个实用的做法是把优先级写成可评审的数字表， 而不是散落在代码的 if/else 里。表能被 FO 评审，代码不能。

四条仲裁规则

  • 同槽位取最高：同一显示位置只保留优先级最高的一个，其余排队
  • 同级按固定次序：优先级相同时按预定义顺序显示，禁止依赖触发先后， 否则台架和实车会不一致
  • 互斥组：语义互斥的报警（如「系统正常」与「系统故障」）定义为互斥，同时成立时以高优先为准
  • 抑制：自检期间、欠压期间、以及存在更高优先报警时，低优先项进入 inhibited， 而不是直接丢弃——被抑制项在条件解除后仍应能恢复显示
踩坑：「抑制」和「清除」写成同一个动作，是报警逻辑最常见的 bug。 结果就是自检结束后该亮的安全带提醒再也不出现，直到下次上电。

去抖与迟滞

报警的触发条件和恢复条件通常是两套阈值，这就是迟滞。 例如电量低于 15% 触发低电量报警，要恢复到 20% 以上才熄灭—— 用同一个阈值会让灯在临界点疯狂闪烁。

  • 时间去抖：条件连续成立 N 个周期才置位，连续不成立 M 个周期才复位
  • 计数去抖：累计帧数满足阈值，适合周期性报文
  • 迟滞带：触发与恢复用不同阈值，宽度按信号噪声水平确定

三个手段可以叠加，但不要三层以上——过度的去抖会让真正的紧急报警延迟数百毫秒， 这在安全件上不可接受。

显示冲突与声音

报警最终要落到有限的屏幕面积和一只蜂鸣器上，冲突不可避免：

  • 文本超长：多语言场景下德语/俄语明显更长，必须提前定截断与换行规则
  • 轮播周期：多个同级报警轮流显示时，单条停留时间不低于 2 秒，否则读不完
  • 声音限频：同一类提示音设置最短间隔，避免「叮叮叮」连响
  • 声音与图标同步：图标出现后 100 ms 内发声，延迟过大会让用户找不到来源

怎么验证

  1. 单触发：逐条验证触发、显示、恢复，确认无残留
  2. 组合触发：按优先级表的交叉组合构造用例，验证仲裁结果
  3. 抖动：让信号在阈值附近反复跳动，确认无闪烁、无状态跳变
  4. 边界：恰好等于阈值时的行为必须写进用例，而不是「差不多」
  5. 抑制恢复：自检/欠压结束后，被抑制的报警应能重新出现

这五类用例覆盖了绝大多数现场问题。剩下的漏网之鱼，通常来自 多个报警共用同一个信号源而该信号本身超时——这类情况要单独设计降级用例。
