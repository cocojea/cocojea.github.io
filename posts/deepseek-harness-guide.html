DeepSeek Harness 上手：把 AI 装进工作流

2026-11-12 · 12 MIN READ · 工具 · AI 工作流

它是什么

DeepSeek Harness（下称 DSH）不是一个聊天框，而是一个跑在本地的 agent 运行时： 你给它一个工作区、一句目标，它在目录里读文件、改文件、执行命令、再自己检查结果。 价值不在「会写代码」，而在读、做、验三步落在同一个上下文里—— 不用人来回复制粘贴，也不会出现「它以为改过了」。

概念含义
工作区 workspace它能读写的目录，也是命令的工作目录；写入默认被限制在这里
会话 session一次任务的上下文，可以继续、可以恢复，也可以开新的
模型路由 modelSettings 里配置的提供商与模型，选中的模型是新会话默认值
工具 tool读写文件、执行 shell、联网检索、派子代理、记计划……
技能 skill一段按需加载的任务说明书，比如「怎么产出规范的 Excel」
插件 / bundle给配置档（profile）加能力或界面，装一次、所有会话生效

三种入口，按场景选：

  • 桌面应用：本地起一个 Web 服务，浏览器打开 127.0.0.1:<端口>，日常用这个
  • dsh web：命令行启动同一个 Web 界面，默认 http://127.0.0.1:3080
  • dsh --profile headless "任务"：跑完一次、打印最终答案就退出，适合脚本和定时任务

配置是按 profile 组织的，profile 本质是一串插件 bundle 的有序叠加， 再叠上你自己的 cordis.patch.yml。所以「桌面版」和「web」可以有两套能力组合，互不干扰。

启动后的两件事

一、配模型

打开 Settings → Models，DeepSeek 卡片只有一个 API Key 输入框，填完保存即可。 密钥是只写不读的：保存后页面只拿到脱敏描述，真正的值落在 $DSH_HOME/.credentials.yaml，设置文件里只留引用。改完下一次请求就生效，不用重启服务。

要接别家模型，点 Add model provider，从内置目录里选（如 anthropic、openai、 moonshotai、zai）填 key；自建网关或中转则切到 Custom model API， 填 Provider ID、Base URL，并选对协议——OpenAI Chat Completions、OpenAI Responses、Anthropic Messages、 Gemini API 四选一。网关说的是哪种协议，就必须选哪种，选错的表现是「key 和地址都对，但每个请求都被拒」。

选模型是在模型选择器里做的，选中的模型会成为新会话的默认值； 已经发过请求的会话仍用它自己日志里记的模型，不会中途换掉。

二、选工作区

点 Choose workspace 添加项目目录并选中。这一步没做，输入框是灰的——这是最常见的「为什么打不了字」。

经验：工作区选项目根目录，不要直接选整个磁盘。范围越小，它越不容易翻错文件， 越界操作也越少，审批弹窗自然就少。

一次会话的五个动作

  1. 读——给路径，别让它猜。「看 src/api/ 下所有路由」远好于「看看这个项目」
  2. 改——小改直接做，大改先要方案；写文件之前先读原文件，避免覆盖掉别人的改动
  3. 跑——命令、测试、构建都可以跑，输出会被读回来，失败了自己接着修
  4. 验——没有验证的「完成」不算完成；让它把验证命令和输出贴出来
  5. 记——多步任务挂一张计划清单，长任务才不跑偏、不漏步

把这五步说清楚，其实就是把一句话需求拆成它能执行的形状：

prompt.txt
目标：给 archives.html 加「工具」分类筛选，只影响归档页。
约束：只改 archives.html 和 assets/js/app.js，不引入新依赖，不动其他页面。
验收：点「工具」后只剩 1 篇；点「全部」恢复 10 篇；刷新后默认仍是全部。

目标 + 约束 + 验收，三行写全，返工少一半。少写哪一项，它就会替你做一项决定， 而那一项往往不是你想要的。

怎么指挥

  • 先让它复述现状：动手前要求「用三句话说明你看到的文件结构和要改的位置」，改错文件的概率立刻下降
  • 探索交给子代理：大范围搜索、读多个文件这类活儿派给子代理，主线只留结论，上下文不被塞满
  • 长任务放后台：跑测试、构建、下载放后台任务，前台继续讨论，完成后再收结果
  • 贴日志先剪裁：几百行日志只留报错前后 20 行；上下文是有限的，省下来的都变成了判断力
  • 让它列假设：信息不全时要求「先列出你的假设和风险，再动手」，比硬猜好得多
  • 发布前必须复核：代码、文案、对外内容，AI 写完都要有人读一遍——它负责产出，你负责判断
反直觉的一点：给的自由度越大，结果越不稳定。把「随便优化一下」换成「把首屏加载压到 1 秒内，只准动图片和缓存头」， 它反而做得更好。

四种扩展

扩展什么时候用粒度
技能 skill有固定流程、固定产出的重复任务按任务加载
插件 / bundle要加工具、加界面、加服务整个配置档
MCP要接外部服务：数据库、内部 API、第三方平台配置档
定时任务每天 / 每周固定时间跑一次的事单条任务
  1. 技能是最轻的扩展：把「先读什么、再算什么、最后怎么排版」写成说明书， 用到时再加载，不占平时上下文。做周报、生成规范表格、解析 PDF，都适合这么固化。
  2. 插件是代码级扩展，用 apply(ctx) 注册工具、命令或界面槽位，装进 profile 后所有会话可见。 写插件前先问一句：这件事能不能用技能 + 现成工具解决？能，就别写代码。
  3. MCP 走标准协议接外部系统，配置成 bundle 即可，不用改 DSH 本身。
  4. 定时任务用一条时间规则（rrule）描述重复，到点把一句指令投进会话。适合每日简报、每周巡检这类「没人催但必须做」的事。

顺序建议：先技能，再 MCP，最后才插件。前两个几乎零维护成本，插件要跟着版本升级走。

沙箱与审批

默认的文件策略是 workspace-write：工作区内随便改，工作区外一律拦截。 拦截不是失败，而是升级成审批——你点同意才放行；没人应答就按拒绝处理。

  • 越界写、装软件、改系统配置都会弹审批，看清楚路径再点
  • 全权限模式等于把整台机器交出去，只在明确知道要干什么时开，并且优先用「单次授权」而不是长期放开
  • 密钥不要贴进对话：用环境变量或凭据文件，让它引用变量名而不是值
  • 对外动作要卡口：push、发邮件、改线上数据之前，先让它给出 diff 或命令清单，你确认后再执行

沙箱的价值不是防 AI「有恶意」，而是防它在错误的地方做了正确的事。 工作区划得准，比事后审查有用得多。

实战：让它改这个博客

这篇文章就是这套流程的产物。博客是纯静态站：blog/ 放源文件，deploy/ 是发布仓库， push 到 main 后由 GitHub Pages 自动构建。整个流程拆成五步，每步可单独重试：

  1. 读结构：让它先读一篇现有文章，抽出 head、导航、目录、正文、页脚的固定骨架
  2. 写文章：复用同一套 class，不新造样式；标题、描述、og 标签一起补齐
  3. 改索引：首页日志列表、归档页年份条目与分类计数、sitemap，一个都不能漏
  4. 自检：跑链接检查与隐私词扫描，确认没有断链、没有把履历信息写进公开页面
  5. 发布并验证：复制到发布仓库、提交、推送，等构建完成后抓线上页面确认
publish.sh
# 1) 同步：只覆盖站点文件，保留 .git
robocopy blog deploy/site /MIR /XD .git

# 2) 提交并推送（发布仓库是独立 git 仓库）
git -C deploy/site add -A
git -C deploy/site commit -m "posts: 新增 DeepSeek Harness 使用教程"
git -C deploy/site push origin main

# 3) 等 1-2 分钟构建，再验证线上
curl -sI https://cocojea.github.io/posts/deepseek-harness-guide.html

几个细节值得记下来：robocopy /MIR 会删掉发布仓库里多余的文件，所以必须 /XD .git； 发布仓库和源目录分开，源目录永远不初始化 git，就不会把 _private/ 里的截图和简历误传上去； 推送成功不等于上线成功，一定要回抓一次线上页面，确认状态码和标题。

经验：把「发布」拆成「复制 → 提交 → 推送 → 验证」四步，而不是交给一个脚本一口气跑完。 出问题时你知道停在哪一步，而不是面对一个半成品仓库。

常见坑

  • 报 MISSING_CREDENTIAL：这个提供商还没存 key。去 Models 页补，或配好它提示的环境变量
  • 报 UNKNOWN_MODEL：选的模型不在已配置列表里，回选择器重选，或把模型 id 加进自定义提供商
  • 网关每个请求都拒：协议或请求形状不对。先试 compat.supportsDeveloperRole: false 和 maxTokensField: max_tokens，这两项能解决大多数 OpenAI 兼容网关
  • 输入框打不了字：要么没选工作区，要么默认模型指向了已删除的提供商
  • 审批一直弹：不是 bug，是任务本身在越界。缩小工作区、拆小步骤，比无脑点同意安全
  • 它说「已完成」但没验：追问「跑了哪条命令、输出是什么」；给不出输出，就当没完成
  • 长会话变慢、答非所问：开新会话，把已验证的结论摘成三五条带过去，比硬撑一个超长上下文有效

最后一句：DSH 的正确用法不是「替我想」，而是「替我做完，并且证明做完了」。 目标写清楚、边界划清楚、验收留一手，它就是一个可靠的执行者；反过来，它只会更快地产生似是而非的结果。
