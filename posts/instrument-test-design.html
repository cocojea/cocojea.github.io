仪表功能测试的设计方法

2026-11-05 · 8 MIN READ · 汽车电子 · 测试验证

测什么

仪表的功能测试容易被简化成「点一遍看看」，但真正的风险集中在四个维度： 输入、输出、状态、时间。任何一个维度的组合被漏掉，问题就会逃到实车。

维度对象典型问题
输入CAN 信号、硬线、按键、传感器超时、抖动、越界值
输出指针、图标、文本、背光、蜂鸣器错位、截断、不灭
状态电源模式、工作状态机、报警状态状态不迁移、残留
时间上电时序、去抖窗口、闪烁频率启动慢、闪错频率

用例设计四板斧

  1. 等价类：把输入域切成有效/无效类，每类取一个代表值。 例如车速分为静止、行驶、超速、溢出四类。
  2. 边界值：等价类的分界点往往就是 bug 聚集地。 指针满量程 ±1、油量报警阈值 ±0.5L、温度 −40/85℃ 都要单独取点。
  3. 状态迁移：画状态机，覆盖每条边，重点是非法跳转—— 例如从 Fault 不经下电直接回 Normal。
  4. 正交表：当「电源模式 × 信号状态 × 报警组合」组合爆炸时， 用正交表把用例数从上百压到十几个，同时保留两两覆盖。
经验：边界值 + 状态迁移这两板斧，通常能抓到全部缺陷的六成以上。 正交表负责「不漏」，前两者负责「抓得深」。

六个必测场景

  1. 冷启动 / 热启动：冷启动看全流程时序，热启动看状态是否被正确重置
  2. 快速上下电：间隔 1 秒内反复断电上电，检验 NVM 与显示残留
  3. 电压拉偏：9V / 12V / 16V 三点，观察显示、通信、报警是否按预期降级
  4. 信号异常：超时、抖动、越界、恒值卡死，四类分别验证降级表现
  5. 总线高负载：人为加负载到 80%，确认实时性劣化时报警仍按时刷新
  6. 休眠唤醒：验证唤醒源、唤醒时延，以及静态电流是否达标

第 2 项最容易被省略，但它能暴露掉电存储窗口不足、文件系统未落盘等一类硬伤， 而且这类问题只会在用户手上出现，台架上永远复现不了。

掉电与 NVM

掉电场景要回答三个问题：写什么、什么时候写、写失败了怎么办。

  • 写什么：小计里程、用户设置、报警历史。总里程通常另有备份机制
  • 什么时候写：变化即写会产生大量擦写，耗尽寿命；定期写又可能丢最后一段。 常见折中是「变化累积阈值 + KL15 下降沿触发」
  • 写失败怎么办：必须校验和 + 双备份 + 重试，且上电时能识别并回滚到上一份有效数据

测试方法很直接：在写入过程中切断电源，重复若干次，检查上电后数据是否一致、 是否出现乱码或归零。这个用例通过率低，往往不是软件写错，而是没有预留足够的保持时间。

自动化怎么做

台架自动化最适合接管「回归集」而不是「探索」。用 CAPL 或 Python + CAN 卡都能做， 关键是用例与断言分离：激励脚本只负责发信号，断言单独写。

test_signal_timeout.can
/* 停止发送车速报文，验证超时降级 */
testcase TC_SpeedTimeout()
{
  const int TIMEOUT_MS = 300;   /* 3 个 100ms 周期 */

  stopPeriodicSend(msgSpeed);
  testWaitForTimeout(TIMEOUT_MS + 200);  /* 留出判定余量 */

  /* 断言：指针应停在失效位置，且置起降级标志 */
  testValidateEqual(getSignal(sigSpeedValid), 0, "speed valid flag");
  testValidateInRange(getSignal(sigSpeedDisplay), 0xFF, 0xFF, "pointer placeholder");

  startPeriodicSend(msgSpeed);
}

注意最后那行恢复发送——自动化用例最常见的连锁失败， 就是上一条用例改了环境没还原，导致后面几十条一起红。

回归与逃逸

  • 冒烟集：30 条以内，覆盖上下电、显示、报警、诊断主链路，每次提交必跑
  • 全量集：版本冻结前跑，包含边界与组合用例
  • 逃逸分析：每个量产问题都要回答「哪条用例应该抓到它、为什么没抓到」， 并把新用例补进集合

逃逸分析的产出不是一份报告，而是用例集的增量。 没有增量的复盘，只是把同一件事重新讲一遍。
