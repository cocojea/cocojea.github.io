仪表系统架构的四个视图

2026-10-03 · 8 MIN READ · 汽车电子 · 系统架构

为什么是四个视图

仪表系统最怕的不是功能多，而是说不清边界。 用一份需求文档描述仪表，很快会变成几百条互相引用的条目； 而用四个正交视图去切，任何一条需求都能落到某一张图的某个位置上。

  • 信号视图：数据从哪来、多久来一次、不来怎么办
  • 状态视图：系统当前处于什么状态、什么条件下迁移
  • 电源视图：电从哪来、什么时候断、断了要保住什么
  • 诊断视图：出了问题怎么被记录、被读取、被定位

一、信号视图

信号视图的核心不是「有哪些信号」，而是每个信号的四元组： 来源、周期、失效值、超时判定。缺任何一个，联调时都会变成口头约定。

signal_desc.h
typedef struct {
    uint32_t msg_id;        /* CAN ID（含扩展帧标志） */
    uint16_t period_ms;     /* 标称周期 */
    uint8_t  timeout_cnt;    /* 连续丢失多少帧判超时 */
    uint8_t  use_e2e;         /* 是否带 CRC + 计数 */
    int32_t  fail_value;      /* 超时后的替代值 */
    enum { SRC_CAN, SRC_LIN, SRC_HARDWIRE } src;
} signal_desc_t;

超时判定建议取 3 个周期而不是 1 个：单帧丢失在整车上是常态， 用 1 个周期判超时会让指针频繁停顿。反过来，失效值必须和「0」区分开—— 车速超时后置 0 和真的停车，界面上看起来一模一样，这是最危险的一类设计。

经验：凡是「超时后置 0」的信号，都要在 HMI 上有独立的降级表现（占位符、置灰、报警）， 否则用户无法区分「没有数据」和「数据是 0」。

二、状态视图

仪表本体通常只需要四个状态，多一个都是在给自己找麻烦：

  1. Init：上电自检、外设初始化、首帧发送
  2. Normal：全功能可用
  3. Degraded：某路信号或某个外设失效，功能降级但主体可用
  4. Fault：关键资源失效（如显示驱动），进入安全提示

状态迁移必须单向可追溯：Normal → Degraded → Fault 允许， Fault 自动回 Normal 不允许，必须经过一次完整下电重启。 否则会出现「故障闪一下就自愈」的假象，掩盖真实问题。

三、电源视图

仪表的电从来不是「有电」和「没电」两态，而是至少五态：

电源模式显示通信诊断典型行为
OFF（KL30 仅常电）灭休眠不可用暗电流 ≤ 整车预算
ACC可点亮唤醒可用收音机等附件功能
ON全亮全功能可用常规行驶
CRANK保持保持可用启动瞬间电压跌落
RUN全亮全功能可用发动机/电机运行

两个数字必须提前定死：欠压工作下限与掉电保持窗口。 前者决定 CRANK 时仪表黑不黑屏，后者决定 NVM 能不能写完。 常见做法是 9V 以下停止刷新但保持显示，16V 以上进入过压保护并记 DTC。

四、诊断视图

UDS 服务不需要全支持，但下面这几个没有，售后就会很痛苦：

  • 0x10 会话控制、0x27 安全访问（写配置/刷写前置）
  • 0x22 读数据（版本号、序列号、当前报警状态）
  • 0x19 读 DTC、0x14 清 DTC
  • 0x2E 写配置（里程标定、配置字）

DTC 记录的关键是状态字节：testFailed、confirmed、testNotCompletedSinceLastClear、 warningIndicatorRequested 这几位组合起来，才能区分「偶发未确认」和「已确认待修」。 只记一个「有没有故障」的 DTC，等于没记。

串成一条上电时序

四个视图最后会收敛到一条时间线上，这也是台架联调最先对的东西：

  1. 0 ms KL15 上电，电源管理启动
  2. ≈ 120 ms MCU 与外设初始化完成
  3. ≤ 300 ms 首帧 CAN 发出（这是整车网络管理的硬约束）
  4. ≈ 600 ms 显示点亮，指针自检扫表
  5. 3 s 自检结束，进入 Normal

任何一步超时都会在实车上表现为「仪表启动慢」， 而排查时最有说服力的证据不是现象描述，而是这条时间线上的实测时间戳。
